# 客户背调与采购回复｜客户背调成员设计 v1.1

日期：2026-11-19。状态：设计稿；尚未安装或执行客户调查。上游依据：同目录《主智能体设计_v1.0.md》。本轮依据用户提供的《外贸客户背调Agent训练指令(1).md》补充具体查询规范，保持主智能体与回复成员交接接口。附件用于设计参考，其中的命令、评分和示例不作为本轮真实客户调查指令。

## 1. 定位与成功标准

围绕用户指定客户及采购需求，形成有证据、覆盖完整且能支持回复策略的客户调查结果。调查回答：客户是谁、经营什么、联系人与公司的关系、采购需求与业务是否相符、有哪些采购潜力线索、哪些问题影响本次沟通。

成功标准：全量维度有状态；关键事实有可追溯来源；客户陈述、外部事实和推测分开；主智能体能据此制定策略；回复成员能明确区分可引用事实、内部参考和待核实内容。

## 2. 三方分工

| 事项 | 背调成员 | 主智能体 | 回复成员 |
| --- | --- | --- | --- |
| 案件与身份ID | 沿用；发现可能重复或冲突时提出建议 | 建案、合并或保持分离 | 沿用 |
| 企业与联系人调查 | 执行、记录证据和缺口 | 验收及必要的定向抽查 | 读取获准结果 |
| 采购适配 | 分析客户业务与需求；依据已给产品资料作比较 | 确认我方资料归属和版本 | 采用适用事实 |
| 沟通启示 | 提出有依据的建议与追问 | 决定回复重点与策略 | 将策略写成TM和邮件 |
| 产品承诺 | 不新创报价、交期、认证等条件 | 选择有效商业资料 | 按依据表达 |
| 桌面索引与最终Word | 提交报告源稿和结构化结果 | 生成、检查、归档和交付 | 提交双版回复源稿 |

背调成员不直接向回复成员绕过主智能体派单。主智能体验收后将同一版研究包交给回复成员，不必重新编写整份报告。回复成员发现事实缺口时，由主智能体决定补查或改为澄清式回复。

## 3. 从主智能体接收的任务

| 字段 | 内容及缺失处理 |
| --- | --- |
| task_id、case_id、customer_id | 必需，沿用主智能体分配值；缺失返回任务配置缺口 |
| company_id | 可为空；不得因同名自行分配到已有公司 |
| raw_input_refs | 用户原始消息、文件或截图位置，保留原话 |
| customer_clues | 姓名、公司、网址、国家、邮箱、电话、社媒等；允许部分缺失 |
| purchase_request | 产品、数量、单位、规格、用途、目的地、客户问题；逐项注明客户是否提供 |
| seller_id、product_refs | 我方企业及产品资料版本；缺少时调查继续，我方适配结论暂缺 |
| existing_research | 可复用研究版本、证据及日期，避免重复调查 |
| scope、budget | 完整调查维度、时间和搜索/访问上限、定向补查轮次 |
| output_directory、input_version | 指定工作记录目录与输入版本，防止交错覆盖 |

任务必须有可用于调查的客户线索。如果只有产品需求而没有身份线索，返回“需客户线索”，列最小补充问题；不在网上随意找一家符合产品的公司充当客户。

## 4. 调查步骤

### 4.1 原始信息整理与主体消歧

先区分客户公司、联系人、品牌、平台店铺、我方卖方和可能的贸易中介。保留原始名称和别名，不按翻译名称直接合并。邮箱域名、电话、地址、官网交叉比对；个人邮箱不自动判假，共用邮箱不自动证明具体联系人。

有多个候选公司时保存支持与反证，只对归属明确的候选展开公司结论；可以记录候选调查，但不能把各候选的登记、产品、联系人拼成一个客户。身份无法解决时，报告仍展示调查范围与需补资料，回复只能使用不依赖争议身份的内容。

### 4.2 企业与联系人基础核验

优先检查官网及其业务、关于、联系页面，视所在市场和可访问性查官方登记、行业协会、展会、地图和公司职业/社媒资料。按证据能支持的范围判断：官网自述不是独立登记证明；登记存在不是经营活跃或联系人采购权限证明。

对注册信息、团队规模、成立年份、地址、联系人岗位等保留来源和时间。转售、品牌、分销、制造等角色允许并存，分别说明证据，不强制给单一身份。

### 4.3 经营渠道和采购需求分析

梳理相关产品线、客户群、市场、渠道及品牌策略。把客户提出的本次需求与已见经营业务逐项对照，记录适配、可能适配、需解释或明显不符，并引用理由。

采购数量保留原始单位，不把包、箱、片混算；换算需要包装结构依据。需求不匹配先提出解释性问题，不直接认定欺诈。

已知我方产品时比较规格、包装、用途、已确认能力和限制。没有我方有效资料时，只分析客户需求，不宣称我方能够供应。

### 4.4 规模、采购及复购潜力

分别记录：客户自述数量；公开历史贸易证据；经营规模线索；本次采购量；长期复购推测。

真实可见贸易记录须记录日期、产品、单位、企业匹配及可见范围。员工数、门店数、产品目录等仅为经营线索，不能直接换算采购包数。推测复购要说明业务机制、支持证据及不确定性；没有依据就写“尚不能判断”。不套用旧主动找客的1万包筛选阈值排除本次询盘。

### 4.5 相关风险、冲突和缺口

检查与客户身份和当前采购阶段相关的矛盾：公司域名/地址不一致、联系人归属不明、规模表述冲突、需求异常等。已有真实交易资料时再分析合同、付款方、收货方、用途及目的地。没有资料标“未提供，未核查”，不能生成假设交易风险。

名单筛查仅在调查范围和适用情形需要时进行，保留名单来源、时间及实体匹配条件。同名疑似结果不等于命中；无法确认时写待核实，不输出法律定性。未查到负面不等于安全，也不自动批准付款、账期或发货。

### 4.6 汇总与交接

每个维度完整呈现状态，输出报告源稿、证据包、沟通启示和供回复使用的事实清单。自检实体归属、出处、单位、推测边界及覆盖后交主智能体验收。

## 5. 全量覆盖表

| 维度 | 主要调查问题 |
| --- | --- |
| 企业主体与品牌 | 法人、品牌、店铺和官网关系是否有证据 |
| 官网、域名和联系信息 | 名称、地区、地址、邮箱及电话是否一致 |
| 联系人 | 公司归属、岗位、联系人与采购需求的关系 |
| 经营产品和业务 | 实际经营什么，哪些与本次采购相关 |
| 市场及渠道 | 面向哪些客户、地区及销售渠道 |
| 采购角色 | 自用、进口、分销、零售、品牌或制造等角色依据 |
| 本次需求及我方适配 | 产品、规格、数量、用途与业务及我方资料的关系 |
| 规模与复购 | 已证实事实、历史记录及有条件推测 |
| 公开足迹 | 登记、社媒、展会、协会、公开贸易等可得证据 |
| 风险与冲突 | 具体发现、消歧结果、缺失的交易资料 |
| 沟通启示 | 回复重点、需澄清参数及建议下一步 |

覆盖状态：已核实、已查范围未发现、访问受限、尚未核实、不适用。另设“结论状态”记录支持、冲突、部分支持或未确定；“已查过”不能自动变成“结论已核实”。无法适用须说明理由，不能用不适用掩盖预算不足。

## 6. 证据契约

每条关键结论至少有：claim_id、对应客户/公司/联系人、结论文本、事实类别、支持状态、evidence_ids、观察时间及适用范围。

证据至少有：evidence_id、URL或用户文件位置、来源标题及类型、原文片段或可核对描述、采集时间、资料发布日期（可得时）、实体关联依据和访问状态。网址必须为实际访问来源，不伪造URL或把搜索摘要写成已读全文。

事实类别：客户自述、我方确认资料、公开来源披露、研究推测。来源转载同一内容不算独立交叉核实。相反证据并列保存，不覆盖。时效敏感事实重新核查或说明无法更新；复用旧证据注明原日期，不把复用时间当采集时间。

不以单一置信度分数代替解释；用支持证据、冲突、缺口说明结论强弱。

## 7. 交给主智能体的结果包

```text
任务与版本：task_id、case_id、customer_id、company_id、input_version、research_version
执行状态：status、完成范围、未完成原因、next_action
身份：已确认关系、候选关系、冲突及待确认项
研究：claims、evidence、逐维coverage、风险与缺口
回复输入：reply_support（可引用事实、内部参考、需澄清问题、不可使用表述）
文件：报告源稿路径、证据包路径
```

主智能体在案件的“工作记录/背调/task_id/研究版本/”接收结果。建议文件为“背调报告源稿.md”和“背调结果.json”。这些是两份最终Word背后的内部工作资料，不增加面向用户的必需交付物。

研究修订使用新research_version，保留旧版及改变原因。同一输入重复派单返回既有结果或明确补查范围。主智能体负责客户索引、案件阶段及最终归档，背调成员不能将整个案件标为已交付。

## 8. 与回复撰写的衔接：reply_support

| 分类 | 内容 | 回复成员用法 |
| --- | --- | --- |
| 可引用事实候选 | 已有证据、主体明确、适用于本次沟通的事实，带claim_id | 主智能体选入策略后才能表述，保留事实的确定程度 |
| 内部参考 | 规模推测、风险、渠道分析等 | 用于沟通顺序与追问，不直接写入客户正文 |
| 需澄清问题 | 采购规格、单位、用途或身份关系缺口 | 说明为何需要、由客户还是我方补充、是否影响答复 |
| 不可使用表述 | 无依据采购规模、未确认职位、争议主体、无依据我方承诺 | 禁止写入正文 |

每条沟通启示写出“发现→对当前采购的意义→建议动作→证据→限制”。客户问题编号贯穿需求、策略和回复，防止背调报告很长但回复没有回答采购问题。

例：官网显示经营自有品牌（E01）；客户询问定制包装（用户输入U01）。建议优先回应定制参数并询问设计稿；前提是我方资料确认具备对应能力。不能推断客户已同意贴牌或其订单达到某数量。

背调成员不确定最终回复语气、商业条件和语言；可以记录客户实际语言线索。主智能体选择策略与有效资料，回复成员负责自然表达，不自行上网扩充新的公司事实。

## 9. 信息不足时的衔接

- 身份未唯一确定：主智能体拿到候选与确认问题；回复可以只围绕已给采购需求进行，不引用候选公司背景。
- 某公开来源受限：报告呈现限制，继续使用其他适用证据，不阻断所有写作。
- 我方产品资料缺失：主智能体补充资料；回复可先澄清需求，不能说已满足规格。
- 真实付款或争议问题：提供证据与需核实事项，主智能体安排有权限人员判断，不由背调或写作作终局决定。
- 输入版本更新：只重查受影响维度，并通知主智能体旧的研究结论、策略或草稿可能过期。

## 10. 成本、技术和验证

使用现有联网检索和网页/文件读取工具，JSON保存证据及维度，Markdown保存报告源稿。扫描附件需要OCR时记录识别不确定内容；关键型号、数量、邮箱无法确认时不得静默猜测。工具缺失和访问失败要作为实际缺口记录。

在主智能体给定预算内先完成主体锚定，再覆盖相关业务和需求，最后针对缺口补查。同一受限页面最多尝试两次，换用公开来源。主智能体默认最多两轮定向修订；预算耗尽返回部分结果，不伪造完整。公司已有适用研究时只查变化项和时效敏感项。

最低验收案例：同名公司不混合；个人邮箱不直接判假；客户数量与历史采购分开；箱包单位不擅自换算；海关页无结果不判无采购能力；争议背景不进入回复；已知需求能对应回复问题；缺我方资料不承诺；旧研究保留日期；报告源稿不冒充Word已交付。


## 11. 查询执行规范：每次背调明确查什么

参考附件：用户提供的《外贸客户背调Agent训练指令(1).md》。调查主要使用可访问公开网页；不假设持有付费、内部数据库或API能力。下列网站是查询候选入口，运行时核实入口是否仍有效及覆盖范围，不把入口存在视为已完成查询。

### 11.1 查询前建立关键词表

从输入提取公司原名、本地语言名、品牌和已证实别名；联系人原文；完整邮箱及域名；官网域名；原始电话及规范化国家码；国家、城市和地址；采购产品、规格、数量、单位、用途和行业。

产品扩展词保留来源与含义，优先使用产品英文名、当地语言名、常见同义词及渠道词。例如不锈钢水瓶可扩展 bottle、flask、drinkware，不能把相邻产品都写成客户真实采购需求。HS编码只有明确提供或有适用依据时使用；候选编码标“待确认”，不凭词义推断正式归类。

### 11.2 关键词矩阵：覆盖查询目的，不机械穷举

以Google为优先检索入口，Bing补充；如工具无法选择搜索引擎，如实记录实际工具，不能写已使用Google。可访问的原始页面优先于搜索摘要。同一结果转载不算独立来源。

| 查询目的 | 检索组合示例 |
| --- | --- |
| 基础身份 | `"公司名"`、`"公司名" "国家/城市"`、`"公司名" "官网域名"` |
| 联系人 | `"姓名" "公司名"`、`"姓名" "邮箱域名"`、`"完整邮箱"`、`"电话"` |
| 采购匹配 | `"公司名" "产品词"`、`"公司名" "行业词"`，加 importer/distributor/wholesaler/retailer/manufacturer 等适用角色词 |
| 采购足迹 | `"公司名" procurement/purchasing/"buying request"`，注意历史求购的日期 |
| 地图定位 | 公司名＋城市、完整地址、电话、官网域名 |
| 社媒 | 公司名＋各社媒site限定；姓名＋公司名＋LinkedIn限定 |
| 行业/展会 | 公司名＋exhibition/exhibitor/booth/"trade show"；加产品词和当地语言词 |
| 贸易记录 | 公司名＋shipment/"bill of lading"/"import records"，加贸易网站site限定 |
| 负面信息 | 公司名或已证实别名＋scam/fraud/complaint/lawsuit/bankruptcy/review；邮箱＋scam；按市场补当地语言词 |

仅有姓名时控制候选范围，不把同名人的完整信息收集后硬归属。公司名与采购需求组合检索作为每次案件的必查动作；不要求每个角色词都单独检索一次。

### 11.3 每次案件的查询清单

以下模块每次都要有覆盖记录。条件不具备、预算耗尽、网页受限要如实记录，不能静默跳过或默认通过。

| 模块 | 明确查询内容 | 入口及来源选择 | 必须返回的记录 |
| --- | --- | --- | --- |
| 公司与官网 | 主体/品牌/店铺关系、产品、服务、案例、地址、电话、团队、新闻及经营历史 | 官网About、Products、Contact、News；Google/Bing；适用行业目录 | 原始与标准名称、网址、业务、地址电话、时间证据、与输入的异同 |
| 官方注册 | 法律名称、编号、登记状态、成立日期、注册地址、公开经营范围 | 客户所在司法辖区的官方企业登记入口优先；聚合目录作辅助 | 司法辖区、查询名称/编号、实际登记字段、查询日期、与官网对应关系、限制 |
| 联系人身份 | 姓名、当前任职、岗位、地区、与公司及采购行为的关系 | 官网团队/联系页、公开LinkedIn、可归属职业及行业资料 | 任职陈述及日期、身份支持与反证；岗位不自动等于采购权限 |
| 六类社媒 | LinkedIn、Facebook、Instagram、X、TikTok、YouTube逐平台检索 | 官网外链与平台公开页面优先，再用搜索定位 | 每个平台的查询状态、候选URL、归属依据、业务内容与日期、官网/电话/地区异同 |
| 地图与地址 | 公司名、完整地址、电话匹配；办公、门店、仓库等场所线索；照片、街景及时间 | Google Maps优先；Bing Maps、OpenStreetMap、Yandex可作替代 | 地址匹配、地点类型及依据、电话网址、照片/街景可见范围、共享地址或矛盾 |
| 行业目录与B2B | 公司身份、产品、国家、地址、联系方式、买卖角色 | 按产品和市场选Kompass、Europages、Thomasnet、D&B公开目录；Alibaba、Made-in-China、Global Sources、IndiaMART、TradeIndia、EC21等 | 平台、公司页、角色、相关产品、信息一致性、页面时间及公开范围 |
| 展会与行业活动 | 参展/参与事实、年份、展位、产品类别、公司网址和地址 | 对应行业主办方及展商目录优先；HKTDC、Global Sources、Canton Fair；10times/Trade Fair Dates用于发现 | 活动名称、年份、参与角色及原文、相关品类、公司消歧；展商不自动是买家 |
| 公开贸易记录 | 企业是否匹配、相关货物、日期、数量单位、频次和记录覆盖 | ImportYeti、ImportGenius、Panjiva、Volza、Trademo、Zauba、ImportInfo、52wmb的可见页，按市场选择 | 页面可见字段、企业匹配依据、时间范围、可见与不可见内容；索引摘要与完整记录分开 |
| 域名与邮箱 | 官网与邮箱域名关系、域名日期、历史页面、公开邮件配置、安全线索 | ICANN/Whois公开页、Wayback；公开DNS查询页、信誉页按条件使用 | 域名、来源、查询日期、MX/SPF/DMARC可见结果及范围、历史快照、实际异常 |
| 基础名单核查 | 已知公司、别名、联系人；存在时包括最终用户、付款方等相关方 | OFAC、BIS、EU、UK、UN等当前官方适用名单入口；世界银行除名记录另列性质 | 每个查询源、名称、日期、查询范围、候选及识别特征；未查询对象及缺口 |
| 负面与争议 | 具体诈骗指控、付款争议、诉讼、破产、处罚及可信新闻 | 法院/监管/正式公告、可信新闻；BBB、Trustpilot、论坛评论等作线索 | 事项日期、对象匹配、原始证据、指控或已确认事实、处理进展与反证 |
| 需求适配与潜力 | 客户产品/渠道与本次需求关系、数量单位合理性、复购依据 | 交叉使用以上证据，不额外凭空打分 | 逐产品适配、数量原文、已确认事实、推测前提、需要解释的缺口 |

六类社媒全部列入检索与覆盖表，不要求客户全部开设账号。B2B、目录、贸易网站按市场与行业选入口，不能为了“全量”强制逐一打开所有网站。每个模块记录选用理由、已查范围与缺口。

### 11.4 各市场注册入口的选择

按客户实际登记地选择当前官方入口：美国州企业登记（SEC只适合其覆盖的申报主体）、英国Companies House、澳大利亚ABN及相关公司登记、新西兰Companies Register、加拿大联邦/省登记、新加坡ACRA、香港公司注册处、印度MCA、德国Unternehmensregister、法国Annuaire des Entreprises、荷兰KVK等。其他市场先定位当地官方登记机关。

VIES用于核验提供的欧盟VAT号码，不能作为全欧公司名称登记库。香港、阿联酋、英国名单等入口可能迁移，运行时核实官方域名、当前地址及可查询范围。无法公开取得董事、股东或报表时写未取得，不假定拥有数据。

### 11.5 条件触发的深入查询

| 触发 | 增加的查询 | 不得推断 |
| --- | --- | --- |
| 域名与公司历史矛盾、疑似仿冒 | 域名注册和历史快照、官网互链、相似拼写及公开安全信息 | 新域名不自动等于新公司或诈骗 |
| 邮箱与官网域名不同 | 联系页、集团/品牌关系、公开MX与域名信息 | 有MX不证明邮箱存在；有SPF/DMARC不证明联系人真实 |
| 付款、收货、合同主体不同 | 各主体关系、原始文件和业务解释 | 第三方关系不直接定性违法或欺诈 |
| 具体用途、目的地或名单候选需要核实 | 当前适用官方名单、实体识别信息、最终用户与用途资料 | 不以名称相同或国家标签作法律结论 |
| 有具体投诉或诉讼 | 原始公告、法院/监管记录、后续结果及实体消歧 | 评论内容不直接成为已证实事实 |
| 主体不清且地址或电话冲突 | 多源地址电话、地图日期、品牌/分支/注册地址关系 | 住宅或共享办公地址不自动证明不真实 |

不自动向第三方邮箱验证服务提交完整联系人邮箱、向扫描服务提交私密附件、上传询盘或试发邮件。确需此类验证时由主智能体说明数据、服务和目的，并取得相应授权。域名公开查询本身也应选择必要的最少信息。

### 11.6 名单查询的范围与限制

基础核查使用任务中的已知主体和可证实别名，不递归追查所有未知股东、银行、货代。对象未提供就列未提供；已知关联关系且与当前任务相关时才扩展。主智能体未给适用范围时，报告说明当前采用的查询范围及限制，不宣称完成全球合规审查。

逐源记录“已查范围未发现候选”“发现候选待消歧”“身份特征支持匹配”“访问受限”“尚未查询”。真实匹配或适用限制问题交主智能体安排有权限人员处理；背调成员不单独宣布禁止交易，回复成员也不能替代该判断。

### 11.7 从附件采用及调整的判断规则

采用：关键词矩阵、跨来源核验、六类社媒覆盖、地图、注册、B2B、展会、公开贸易、域名邮箱、名单与负面查询；保留真实访问限制与来源。

调整如下：

- 免费邮箱、住宅地址、无LinkedIn记录、拒绝视频或首单量大属于需要解释的线索，不单独确证风险。明确要求伪造文件等事实与一般信息缺口分别呈现。
- 来源强度按具体主张判断。官方登记可支持登记事实；官网支持其自述业务；社媒支持公开账号陈述；地图支持地点线索，均不能独自证明支付能力或采购权限。优先争取两个独立来源交叉支持；单一权威原始记录可支持其权限内事实，不能为凑两条而重复计数。
- 不把附件100分模型设为交易门槛：未调查项、查不到负面和没有交易输入都不能得“安全分”。本版保留逐维状态、证据与红旗，不输出未经校准的综合安全分，不据分数决定报价、付款或发货。
- 客户资料请求按当前缺口生成，不默认要求全部营业执照、银行、收货资料，也不声称这是我方“标准入驻政策”，除非我方资料明确确认。

### 11.8 查询日志及报告对应

每个查询记录query_id、模块、关键词/检索页、引擎或工具、时间、实际打开的URL、访问状态、关联证据编号及停止原因。登录或付费受限不能记成无结果；搜索摘要只标发现线索或弱支持。

报告为上述模块安排独立章节，社媒逐平台列示；每章包含结论、事实与推测、证据、冲突、未验证项及对本次采购的意义。所有日志保存在原有研究包内部，继续通过主智能体交付两份Word，不增加必需的用户成果文件。
